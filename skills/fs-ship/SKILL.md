# fs-ship — выложить и убедиться, что измеряется

Задача: чтобы живые люди из сегмента могли открыть продукт по ссылке, а пользователь видел события, по которым примет решение в `fs-learn`. Красивый деплой без событий — бесполезен для проверки гипотезы.

## Правила шага

- Пиши на языке пользователя; команды и имена сервисов — как есть.
- **Всё, что стоит денег или видно снаружи, — только с явного «да» пользователя:** регистрация в сервисах, платные тарифы, деплой, изменение DNS, отправка писем. Аккаунты создаёт и оплачивает сам пользователь; агент даёт шаги и проверяет результат.
- Секреты — только в переменных окружения хостинга. Ни в коде, ни в репозитории, ни в чате.
- Новичку — каждый шаг с тем, что должно получиться, и как это проверить. Опытному — коротко.
- Хостинг выбирается по общему алгоритму из `references/hosting.md`. Конкретные провайдеры в справочник пока не внесены — называй варианты, которые подходят по критериям, и честно говори, если не уверен в актуальных условиях.

## Шаг 0. Что выкладываем

1. Найди `.fs/state.yaml`, `04-spec.md` (события и kill/continue) или `03-test.md` (лендинг), `05-architecture.md` (стек, секреты), `project-context.md`.
2. Определи предмет:
   - **страница теста** из `fs-test` (лендинг, форма, предзаказ);
   - **приложение** после эпика E1 или всех эпиков из `fs-build`.
3. Проверь готовность: все тесты проходят, истории E1 в статусе `review` или `done`, для UI — гейт `fs-design` пройден. Не готово → скажи, что именно, и спроси, выкладывать ли всё равно; при «да» — запись в `skipped_gates`.

## Шаг 1. Профиль пользователя

Спроси одним пакетом (если ещё не записано в `07-ship.md`):
1. **В какой стране вы и ваши клиенты?**
2. **Чем будете платить за хостинг** — карта какой страны, другой способ?
3. **Уровень:** делали ли раньше деплой?

Профиль:
- **РФ** — оплата российской картой и/или клиенты из России (важно для хранения персональных данных);
- **зарубеж** — иностранная карта и клиенты вне России.

Если клиенты в одной юрисдикции, а оплата из другой — профиль по **клиентам** (законы о данных), оплату решаем отдельно и говорим об этом прямо.

## Шаг 2. Тип проекта

| Тип | Что нужно от хостинга |
|---|---|
| Статическая страница | раздача файлов, HTTPS, свой домен |
| Приложение с сервером | запуск сервера, переменные окружения, логи |
| Приложение с базой | управляемая база с автоматическими бэкапами |
| Бот | постоянный процесс или вебхук, переменные окружения |
| Фоновые задачи | расписание запусков |

## Шаг 3. Выбор хостинга

Пройди алгоритм из `references/hosting.md` и предложи **два варианта** с плюсами и минусами для этого пользователя: цена на старте, сложность, где лежат данные, как деплоить. Выбор — за пользователем. Запиши решение и причину в `07-ship.md`.

## Шаг 4. Секреты

1. Возьми список секретов из `05-architecture.md` (или собери по коду: ключи API, пароли базы, токены).
2. Проверь, что `.env` и похожие файлы в `.gitignore`.
3. Проверь, не попали ли секреты в историю git (поиск по характерным строкам ключей). Попали → секрет считается скомпрометированным: пользователь выпускает новый, старый отзывает. Очистка истории не заменяет замену ключа.
4. Перечисли пользователю, какие переменные завести в хостинге, — **без значений**.

## Шаг 5. Деплой по шагам

Для выбранного хостинга и стека составь шаги в `07-ship.md` — таблица «шаг → команда или действие → как проверить». Обычно:

1. Аккаунт и проект в хостинге (делает пользователь).
2. Подключение репозитория или загрузка сборки.
3. Команды сборки и запуска; версия среды выполнения.
4. Переменные окружения.
5. База данных: создание, миграции, проверка подключения.
6. Первый деплой — **после подтверждения пользователя**.
7. Проверка: открыть URL, пройти путь до Aha самому.

Ошибка на шаге — читаем логи хостинга, а не гадаем. Найденная особенность («перед деплоем нужна миграция») — строка в `project-context.md`.

## Шаг 6. Домен и HTTPS

- Для первого теста хватит адреса от хостинга. Свой домен — если важен для доверия клиентов или нужен для почты.
- Свой домен: регистратор, доступный в профиле пользователя; DNS-записи по инструкции хостинга; изменение DNS — с подтверждения пользователя; ожидание распространения записей.
- HTTPS — автоматический сертификат хостинга; переадресация с `http` на `https`; проверка, что сертификат действителен.

## Шаг 7. Аналитика

1. Подключи сервис аналитики, допустимый на рынке пользователя и подходящий профилю.
2. Пройди путь до Aha сам — с телефона и с компьютера.
3. Для каждого EV из `04-spec.md` (или метрики из `03-test.md`) проверь в отладочном режиме или отчёте реального времени, что событие **пришло** с нужными свойствами. Отметь в таблице `07-ship.md`.
4. Исключи свои визиты, если сервис это позволяет, — иначе они исказят первые числа.
5. Не пришло → чиним до релиза: без событий гипотезу нечем проверить.

## Шаг 8. Предрелизный чек-лист

Пройди `references/release-checklist.md` вместе с пользователем: доступность, персональные данные, бэкапы, ошибки и логи, откат, обратная связь. Пункты, которые пользователь сознательно откладывает, — в `07-ship.md` с причиной.

## Шаг 9. Записать

1. `docs/fs/h-NNN/07-ship.md` по `template.md`: профиль, хостинг и почему, шаги деплоя, домен, секреты (только названия), таблица событий, чек-лист, `url` во frontmatter.
2. `.fs/state.yaml`: `stage: ship`, `next: fs-learn` — с датой из раздела «Kill / continue» спецификации (или датой решения теста).

## Шаг 10. Гейт выхода

- **URL открывается** с телефона и с компьютера по HTTPS.
- **События EV приходят** в аналитику — каждое из `04-spec.md`, либо метрика теста.

Не выполнено → покажи, что именно, и чем грозит («люди придут, а решение принять будет не по чему»), спроси, продолжать ли; при пропуске — запись `{gate: fs-ship, reason: "…"}` в `skipped_gates`.

## Шаг 11. Итог пользователю

5–8 строк: URL; где хостинг и сколько стоит в месяц; какие события приходят; что отложено из чек-листа; как откатить; когда смотреть результаты — дата для `fs-learn`; кому и как отправить ссылку первым (из плана теста или сегмента во frame).

## Чего не делать

- Не регистрировать аккаунты и не включать платные тарифы за пользователя.
- Не хранить и не показывать значения секретов.
- Не выкладывать без проверки событий — «посмотрим потом» превращается в «не по чему решить».
- Не строить сложную инфраструктуру (несколько окружений, кластеры) для первой проверки гипотезы.
