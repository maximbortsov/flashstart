# Анализ: Impeccable

Версия: `abf5779` (2026-10-14). Лицензия: Apache 2.0 (+ NOTICE.md: часть платформенных справок выведена из MIT-проекта). Конспект своими словами.

## 1. Что делает каждая часть

| Часть | Что делает |
|---|---|
| **Скилл `impeccable`** | Один скилл, ~25 подкоманд. Ядро короткое (~90 строк), по команде подгружается файл из `reference/`. |
| **Движок (Rust, `crates/`)** | Бинарник, который вызывается из скилла: загрузка контекста, детектор, live-режим в браузере. |
| **Детектор** | 59 детерминированных правил, работает без LLM: `npx impeccable detect <путь\|URL>`, есть JSON для CI. Ловит и «ИИ-признаки» (цветная полоса сбоку у карточек, фиолетовые градиенты, «пружинящие» анимации, свечения), и общие дефекты (длина строки, тесные отступы, мелкие зоны нажатия, пропуски уровней заголовков). |
| **Хук** | После правки UI-файла агентом автоматически запускает детектор и возвращает находки в диалог. |
| **CLI, расширения браузера/VS Code** | Детектор и live-итерации вне агента. |

### Команды по группам
- **Построение**: `init` (контекст продукта → `PRODUCT.md`), `shape` (интервью и бриф до кода), `document` (описать существующую визуальную систему → `DESIGN.md`), `extract` (токены и компоненты).
- **Оценка**: `critique` (UX-ревью: иерархия, когнитивная нагрузка, «красные флаги» персон, оценка здоровья дизайна), `audit` (доступность, производительность, темы, адаптивность, целостность реализации).
- **Доводка**: `polish` (финальный проход), `distill` (убрать лишнее), `harden` (ошибки, переполнение текста, i18n, граничные случаи), `onboard` (первый запуск, пустые состояния), `clarify` (тексты интерфейса), `adapt`, `optimize`.
- **Стилизация** (вне MVP FlashStart): `bolder`, `quieter`, `colorize`, `typeset`, `layout`, `animate`, `delight`, `overdrive`.
- **Итерации в браузере**: `live`, `generate`.

## 2. Ключевые идеи (пересказ)

1. **Факты о продукте отдельно от внешнего вида.** `PRODUCT.md` хранит пользователей, их задачи, назначение продукта, позиционирование, ограничения, голос, доказательства, доступность — и явно не хранит палитры, шрифты, концепты. Визуальная система — отдельно, в `DESIGN.md`.
2. **Режим поверхности.** Выбирается по экрану, а не по продукту: «убедить» (лендинг, цены), «работать» (приложение, дашборд), «читать» (документация), «показать» (портфолио). От режима зависит, что важнее — выразительность или привычность и скорость задачи. Лендинг инструмента — это «убедить», даже если сам продукт — «работать».
3. **Нижняя планка качества перед любой правкой UI**: контраст, ритм отступов, длина строки, состояния (hover, disabled, loading, error, empty), фокус клавиатуры, тексты на языке продукта, все требования брифа находимы за секунды.
4. **Список отказов** — дефолты, к которым модель тянется, когда не принимает решения: одинаковые карточки «иконка + заголовок + текст», шаблон «большая цифра + подпись», надписи-«надзаголовки», градиентный текст, стекло ради стекла, моноширинный шрифт как костюм «технологичности», эмодзи вместо иконок, светлая/тёмная тема «по категории», модалка без необходимости.
5. **Проверка ограниченным числом проходов**: построить целиком → один пакетный осмотр (десктоп и мобильный) → починить всё найденное разом → максимум ещё один осмотр → стоп. Бесконечная самопроверка тратит ресурсы.
6. **Бриф важнее вкуса модели**; доработка сохраняет существующую идентичность, редизайн заменяет её целиком — не смешивать.
7. **Интервью до кода** (`shape`): 2–3 вопроса за раунд — назначение, кто приходит и в каком состоянии, что главное сделать; затем реальный контент и его диапазоны, важные состояния, ограничения.
8. **Устойчивость** (`harden`): переполнение текста, длинные/пустые значения, ошибки сети и прав, локализация, валидация ввода.
9. **Тексты интерфейса** (`clarify`): кнопка называет действие, ошибка называет проблему и выход, пустое состояние объясняет, что здесь будет и как начать.

## 3. Сверка с FRAMEWORK.md §2

| В FRAMEWORK «берём идеи» | Есть | Комментарий |
|---|---|---|
| Файл контекста продукта (генерируем из frame) | да, `PRODUCT.md` | См. Р1 — совпадение имени файла. |
| Файл дизайн-системы | да, `DESIGN.md` | Тоже совпадает с BMAD V7. |
| Сформировать → раскритиковать → проверить → отполировать | да: shape → critique → audit → polish | |
| Список антипаттернов ИИ-интерфейсов | да: craft-floor + 59 правил детектора | Свой список, своими словами и меньше (~20 пунктов). |
| UX-тексты, пустые/ошибочные состояния | да: clarify, harden, onboard | |

| В FRAMEWORK «режем» | Подтверждено |
|---|---|
| Анимации, «вау»-эффекты | `animate`, `delight`, `overdrive` — режем |
| Live-режим | `live`, `generate` — режем |
| Тонкая стилизация | `bolder`, `quieter`, `colorize`, `typeset` — режем |

### Что FRAMEWORK не упоминает, но стоит взять (идеи)
1. **Режим поверхности** (убедить / работать / читать) — одно поле в брифе экрана. Лендинг из `fs-test` = «убедить», прототип из `fs-build` = «работать». Резко меняет чек-лист.
2. **Ограниченное число проходов проверки** — правило для `fs-design`: максимум 2 раунда осмотра, иначе цикл «правлю → смотрю» съедает сессию.
3. **Скриншоты в двух ширинах** как обязательный шаг аудита (Playwright доступен).
4. **Реальный контент в макете** — никакого lorem ipsum; данные правдоподобные, с одним «неудобным» состоянием.
5. **Детектор как опциональная проверка в DoD** — если `npx impeccable detect` доступен, запускать в `fs-build` для UI-историй (уже в FRAMEWORK §6, подтверждаю, что CLI это позволяет без LLM).

## 4. Что переписываем своими словами

| Идея | Как выглядит в FlashStart |
|---|---|
| Контекст продукта | `PRODUCT.md`, генерируется `fs-spec` из frame: сегмент, Core/Big Job, SC, Aha Moment, голос, ограничения. Без визуальных решений. |
| Дизайн-система | `DESIGN.md` от `fs-design`: токены (цвет, шрифт, отступы, радиусы), 3–5 компонентов, режим поверхности. |
| Цикл | 4 шага `fs-design`: бриф экрана → набросок → критика по Job и SC → аудит по чек-листу → полировка. |
| Антипаттерны | `fs-design/references/antipatterns.md` — свой список, сгруппированный по «чем это вредит клиенту» (обман внимания, шум, недоступность, ложные обещания), а не по CSS-признакам. |
| Состояния и тексты | `fs-design/references/states-and-copy.md`: пустое, загрузка, ошибка, успех, переполнение; правила текстов в связке с Job-языком. |
| Интеграция | Если найден установленный Impeccable — `fs-design` предлагает `critique`, `audit`, `polish`, `detect`; ничего не копирует. |

## 5. Расхождения и риски

- **Р1. Имя и место `PRODUCT.md`.** Impeccable ищет `PRODUCT.md` (и `DESIGN.md`) в корне проекта и при наличии обновляет его, а не создаёт свой. FRAMEWORK кладёт артефакты в `docs/fs/h-NNN/`. Варианты: (а) `fs-spec` пишет `PRODUCT.md` в корень продукта — тогда Impeccable подхватит контекст бесплатно, но файл общий для всех гипотез; (б) держать в `docs/fs/h-NNN/` и при интеграции копировать/линковать. Предлагаю (а): продукт один, гипотезы — его итерации; `fs-spec` обновляет файл и записывает `hypothesis` в frontmatter. Нужно решение автора.
- **Р2. Совместимость формата `PRODUCT.md`.** Чтобы Impeccable его понял, разделы должны быть близки по смыслу (пользователи, назначение, позиционирование, ограничения). Общие заголовки вроде «Users» не охраняются, но копировать их набор и порядок целиком не будем — свой формат + совместимость по смыслу.
- **Р3. Детектор vs «свой чек-лист».** Детектор формальный (CSS/HTML), чек-лист FlashStart будет смысловым. Это не замена, а разные уровни; формулировку FRAMEWORK §2 «свой чек-лист вместо детектора» предлагаю уточнить: «свой смысловой чек-лист; детектор Impeccable — опционально».
- **Р4. Модальная лексика Impeccable** (жёсткие запреты вроде «никогда надзаголовки») — его вкус, а не универсальная правда. В FlashStart правила формулируем через вред для клиента и оставляем право брифа их отменить.
