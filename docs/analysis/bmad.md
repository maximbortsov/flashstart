# Анализ: BMad Method

База: стабильная **v6.12** (`bab9082`, ветка `V6.12`). Для справки — V7 preview (`8f0d50e`), см. §5. Лицензия: MIT; товарные знаки «BMad», «BMad Method» не лицензируются. Конспект своими словами.

> v6.12 — переходная версия: классические скиллы v6 (`create-story`, `dev-story`, `sprint-status` и др.) помечены устаревшими и оставлены как «шимы», официальный путь реализации — `build`. Поэтому часть того, что FRAMEWORK.md изначально брал из BMAD (story-файл с задачами, dev-story), устарела уже в стабильной версии.

## 1. Что делает каждая часть (v6.12)

### Каркас
- **Цикл доставки**: прояснить → спланировать → построить и проверить → извлечь уроки. Войти можно с любой точки; мелкая правка — сразу в build.
- **Установка** через `npx bmad-method install`; скиллы рендерятся с настройками проекта (`customize.toml`, `_bmad/`).
- **`bmad-help`** — советует следующий шаг.

### Исследование и идея (опционально)
- **brainstorming**, **forge-idea** (допрос идеи «персонами» до решения делать/бросить), **deep-recon** (исследование под решение), **prfaq** (пресс-релиз будущего продукта + жёсткие вопросы), **product-brief** (1–2 страницы + приложение с отвергнутыми вариантами), **advanced-elicitation** (заставить модель пересмотреть свой ответ приёмами вроде пре-мортема).

### Планирование
- **prd** — создать / обновить / проверить PRD.
- **ux** — описание того, как продукт выглядит и как себя ведёт.
- **architecture** — короткий документ только с решениями, которые держат согласованными независимо собираемые части.
- **spec** — сжатие любого входа в короткое ядро (зачем, возможности, ограничения, что не делаем, сигнал успеха) + файлы-компаньоны.
- **create-epics-and-stories** — разбивка требований на эпики и истории. Документ начинается с инвентаря требований (функциональные, нефункциональные, из UX, из архитектуры) и **карты покрытия FR**, дальше эпики с целью и истории в форме «как {роль} хочу {возможность}, чтобы {польза}» с AC «дано / когда / тогда».
- **sprint-planning** — два хода:
  1. **Гейт готовности**: «сможет ли разработчик реализовать эпики, не придумывая решений, которых нигде нет?» Проверяет трассировку в обе стороны (требование без истории, история без требования), отсутствие зависимостей эпиков «вперёд», независимость историй, записанность архитектурных и UX-решений, конфликты между документами. Вердикт: PASS / CONCERNS / FAIL; при FAIL называет скилл, который исправит пробел.
  2. Генерация `sprint-status.yaml` скриптом (статусы эпиков и историй).
- **project-context** — блок правил в `AGENTS.md`. Принцип: записывать только то, что дорого получить из репозитория (политики, отклонения от умолчаний, правильные команды, наблюдённые ошибки агента); описание стека и структуры — вредно (по исследованиям, на которые ссылается BMAD, нет роста качества и +20% стоимости). Старый `generate-project-context` переадресует сюда.

### Реализация
- **build** — главный скилл:
  1. *Прояснить и выбрать путь* — по коду и документам; лёгкий путь (один заход) или полный (письменный план).
  2. *План* — компактный файл (900–1300 токенов, >1600 — риск «гниения контекста»): намерение (проблема + подход), границы «всегда / никогда», матрица «сценарий → вход → ожидаемое поведение → обработка ошибки», открытые вопросы. Часть «намерение и границы» **замораживается после одобрения** человеком.
  3. *Реализация* с тестами.
  4. *Ревью* независимыми ревьюерами-линзами.
  5. *Показ результата*, синхронизация статуса в `sprint-status.yaml`.
  Для эпика собирается сжатый контекст `epic-N-context.md` — только то из PRD/архитектуры/UX, что относится к эпику.
- **build-auto** — то же без человека.
- **code-review / review** — линзы: состязательная (найди ≥10 проблем; ноль находок — думать дальше), охотник за граничными случаями, пробелы в проверке, структура, текст.
- **qa-generate-e2e-tests**, **correct-course** (влияние крупного изменения на PRD/эпики/архитектуру), **retrospective** (разбор эпика по следам с вердиктом приёмки), **walkthrough** (проводка человека по изменению).

### Устаревшие (шимы v6)
`create-story` (story-файл с задачами и подзадачами, журналом агента, списком файлов), `dev-story` (выполнить все задачи истории за один заход, не останавливаясь), `quick-dev`, `sprint-status`, `create-prd`, `create-architecture` и др. Все отправляют к `build` / новым скиллам.

### Роли
Агенты-персоны (аналитик, PM, архитектор, разработчик, UX) — точки входа к тем же скиллам; party-mode — групповое обсуждение агентов.

## 2. Сверка с FRAMEWORK.md §2 (с учётом решений автора)

| Что берём | В v6.12 | Как используем |
|---|---|---|
| PRD → архитектура → эпики/истории | да | `fs-spec` → `fs-plan` |
| Короткие истории с AC «дано / когда / тогда» | да (create-epics-and-stories) | `stories/*.md`, создаёт `fs-plan` |
| План перед реализацией | да (build) | `fs-build` дописывает план и задачи в story-файл |
| Гейт готовности, трассировка в обе стороны | да (sprint-planning) | гейт `fs-plan` + `trace-check` (новое правило 7: каждый FR покрыт историей) |
| Минимальный контекст проекта | да (project-context) | `project-context.md` — только неочевидное |
| Цикл «план → реализация → ревью» с тестами | да (build) | `fs-build` |
| Состязательное ревью + граничные случаи | да (линзы) | `review.md`, две линзы |
| Вход по размеру задачи | да (лёгкий/полный путь, нужен ли план) | треки S / M / L |
| Learn & adjust | схема цикла + retrospective + correct-course | `fs-learn` (но про рынок, а не процесс) |

| Режем | Подтверждено в v6.12 |
|---|---|
| Агенты-персонажи, party mode | есть — режем |
| Шардинг документов | нет; вместо него ядро spec + компаньоны и epic-context — режем |
| Sprint-планирование и `sprint-status.yaml` | есть — режем статусы; берём только гейт готовности |
| Ретро как церемония | есть (retrospective) — режем |
| Enterprise-тестирование, game dev, creative | вынесены в модули — режем |

## 3. Что переписываем своими словами

| Идея | Как выглядит в FlashStart |
|---|---|
| Инвентарь требований и карта покрытия | В `04-spec.md` — список FR; в `05-architecture.md` / по историям — `refs` во frontmatter; карту строит `trace-check`, руками не ведём. |
| Короткая история | Цель (1–2 предложения), ссылки на FR, AC «дано / когда / тогда». Без задач. |
| План перед кодом | Секция «план» в story-файле: подход, границы «всегда / никогда», таблица сценариев и ошибок, открытые вопросы. Намерение не меняется без согласия человека. |
| Объём | История — одна цель, одна сессия (ориентир ~500 строк кода); план — не длиннее ~1,5 тыс. токенов. |
| Гейт готовности | Вопрос «можно ли реализовать, не придумывая решений?» + `trace-check` (орфаны в обе стороны). Предупреждает, не блокирует. |
| Ревью | Две линзы: «сломай это» и «граничные случаи». Триаж: своё — чинить; старое чужое — в `deferred.md`; ошибка цели — назад в `fs-spec`. |
| Контекст эпика | Не отдельный файл: `fs-build` читает только FR и SC, на которые ссылается история. |
| Минимальный контекст проекта | `project-context.md`: команды, запреты, отклонения от умолчаний, наблюдённые ошибки агента. |

## 4. Расхождения и риски

- **Р1.** Story-файл с задачами и `dev-story` устарели уже в v6.12 — **решено**: истории короткие, план дописывает `fs-build`.
- **Р2.** `project-context.md` со стеком — **решено**: только неочевидное.
- **Р3.** Марка «BMad» — только в README/inspiration как «вдохновлено» (соблюдено).
- **Р4.** Нет аналога `fs-ship` — деплой вне метода BMAD, `fs-ship` целиком свой.
- **Р5. Новое.** В v6.12 трассировка в обе стороны — часть гейта готовности. В правилах FRAMEWORK §5 было только «история → FR»; добавлено правило 7 «FR → история».

## 5. Справка: чем V7 отличается от v6.12

Учитывать не будем (решение автора), но полезно знать: в V7 удалены `create-epics-and-stories` и `sprint-planning` — их заменил `ticket` (дерево `tickets.toml`, план истории как носитель статуса); шимы v6 убраны; `build` и `spec` почти без изменений.
