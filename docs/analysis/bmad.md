# Анализ: BMad Method

Версия: V7 preview `8f0d50e` (2026-10-13), сверка с веткой v6.12 `bab9082`. Лицензия: MIT; товарные знаки «BMad», «BMad Method» не лицензируются. Конспект своими словами.

> **Важно.** FRAMEWORK.md описывает BMAD в терминах v6 (story-файл, dev-story, project-context.md, sprint-статусы). В V7 эти части заменены, а в v6.12 уже стоят «шимы», перенаправляющие на новые скиллы. Релиз V7 ожидается 2026-10-16 — hash стоит перепроверить после релиза.

## 1. Что делает каждая часть (V7)

### Каркас
- **Цикл доставки**: прояснить идею → спланировать → построить и проверить → извлечь уроки и скорректировать план. Войти можно в любой точке: мелкая правка сразу идёт в build.
- **Хаб `bmad`**: отвечает на вопросы, советует следующий скилл, ставит/обновляет установку.
- **Шаблонизатор**: SKILL.md — тонкая обёртка, которая через `uv run` рендерит workflow с подстановкой настроек проекта (`customize.toml`). Скилл не работает без установки.

### Исследование и идея (опционально, не стадии)
- **brainstorming** — фасилитация идей.
- **forge-idea** — допрос сырой идеи несколькими «персонами» до решения «делать / бросить».
- **deep-recon** — исследование под решение, с источниками.
- **prfaq** — пресс-релиз будущего продукта + жёсткие вопросы клиентов и команды, финальный вердикт.
- **product-brief** — 1–2 страницы о продукте + приложение с отвергнутыми вариантами.

### Планирование
- **prd** — создание / обновление / валидация PRD. Нужен, только когда несколько людей должны согласовать продукт или несколько эпиков не должны разойтись.
- **spec** — центральный скилл. Сжимает любой вход в «ядро» из пяти полей: зачем, что должно уметь, ограничения, что не делаем, сигнал успеха. Всё, что не влезает, — в файлы-компаньоны. Пробелы — в список открытых вопросов.
- **ux** — `DESIGN.md` (как выглядит) и `EXPERIENCE.md` (как ведёт себя).
- **architecture** — короткий документ только с решениями, которые держат согласованными независимо собираемые части.
- **ticket** — дерево работы: инициатива → эпики → истории/баги в `tickets.toml`; файл истории необязателен.
- **project-context** — блок в `AGENTS.md`. Исследования, на которые ссылается BMAD: описание того, что агент и так может прочитать в коде, не помогает и стоит +20% токенов; помогают только неочевидные правила, политики, отклонения от умолчаний и наблюдённые ошибки агента.

### Реализация
- **build** — главный скилл. Шаги: прояснить намерение по коду и документам → выбрать путь (лёгкий «oneshot» или полный с письменным планом) → реализовать → ревью независимыми ревьюерами → показать результат. Сессия ≈ одна цель, ≈ 500 строк кода. План — 900–1600 токенов, AC в форме Given/When/Then, без TBD. Ревью — триаж: своё чинится, чужое старое уходит в `deferred-work.md`; если ошибка в плане или цели, возврат на тот уровень.
- **build-auto** — то же без человека, для конвейера.
- **code-review / review** — набор «линз»: состязательная (найди ≥10 проблем, ноль находок — подумай ещё), охотник за граничными случаями, пробелы в проверке, структура, текст.
- **qa-generate-e2e-tests** — e2e/API-тесты для готовой функциональности.
- **correct-course** — оценка влияния крупного изменения на PRD, эпики, архитектуру.
- **retrospective** — разбор завершённого эпика по оставленным следам (план, диффы, коммиты) с вердиктом приёмки.

### Роли и прочее
- Агенты-персоны (аналитик, PM, архитектор, разработчик, UX) — теперь лишь «точки входа» к тем же скиллам.
- party-mode, toolsmith, eval, customize — групповые обсуждения, сборка скиллов, оценка, переопределения.
- Отдельные модули: игры, творческий набор, enterprise-тестирование, автономный цикл по эпику.

## 3. Что переписываем своими словами

| Идея | Как выглядит в FlashStart |
|---|---|
| Короткое ядро спецификации | `04-spec.md`: зачем (ссылка на J/SC), FR, ограничения, не делаем, сигнал успеха (= EV + kill/continue). |
| План истории перед кодом | Секция «план» внутри `stories/S1.2.md`, заполняется `fs-build` на старте, с AC «дано / когда / тогда». |
| Объём истории | Правило: история — одна цель, укладывается в одну сессию (ориентир ~500 строк кода). |
| Независимое ревью | `review.md`: минимум две линзы — «сломай это» и «граничные случаи»; DoD требует ≥3 закрытых находок или обоснованное «не найдено» (уже в FRAMEWORK §6). |
| Триаж находок | Своё — чинить; чужое — в `deferred.md`; ошибка цели — вернуть в `fs-spec`. |
| Минимальный контекст | `project-context.md` только с тем, чего нет в коде: команды, запреты, отклонения от умолчаний, наблюдённые ошибки. |
| Архитектура только из решений | `05-architecture.md`: стек + короткие ADR, без пересказа кода. |
| Вопросы вместо догадок | Неясное → открытый вопрос в артефакте, а не выдумка. |

## 4. Расхождения и риски

- **Р1. Story-файлы.** FRAMEWORK §4: `fs-plan` пишет `stories/*.md` целиком заранее. V7 показал, что заранее расписанные задачи быстро устаревают; план пишется перед реализацией. Предложение: `fs-plan` создаёт истории коротко (цель, FR, AC), а задачи и план дописывает `fs-build`. Трассировка (§5 правило 3) не страдает.
- **Р2. `project-context.md`.** Исследования, приведённые в BMAD, говорят, что описание стека и структуры вредит (+20% стоимости, без роста качества). Предложение: оставить файл, но ограничить содержимое неочевидными правилами; альтернатива — писать этот блок прямо в `CLAUDE.md` продуктового репо, где агент его точно прочитает. Нужно решение автора.
- **Р3. Ссылка «BMAD» в FRAMEWORK §2.** Внутренний документ — допустимо. В README — только «вдохновлено BMad Method», без использования марки в названиях (соблюдено).
- **Р4. Нестабильность V7.** Ветка в альфе, релиз завтра. Анализ по hash `8f0d50e`; после релиза — перепроверить сводку (особенно `build`, `spec`, `ticket`).
- **Р5. Нет аналога `fs-ship`** в BMAD — деплой там вне метода. Для `fs-ship` идей из BMAD нет; это собственная часть FlashStart.
