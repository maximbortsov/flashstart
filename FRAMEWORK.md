# FlashStart — фреймворк проверки гипотез «от Job до интерфейса»

> Префикс скиллов: `fs-`. Артефакты пишутся на языке пользователя.
> Цель: соло-фаундер / технический продакт проводит гипотезу под ключ — от Job клиента до работающего и не «слопового» интерфейса — и как можно раньше убивает слабые гипотезы.

Источники: **NMT / AJTBD** (что и зачем), **BMAD** (как превращать решение в код), **Impeccable** (качество UI). Источники — только вдохновение: фреймворк оригинальный (см. §2).

---

## 1. Принципы (6, остальное вырезано)

| # | Принцип | Откуда |
|---|---|---|
| P1 | Любая работа — гипотеза с заранее записанным kill-критерием. Ввод пользователя тоже гипотеза. | NMT: RAT, producer-contract §3 |
| P2 | Решения выводятся из Job клиента и его критериев успеха, а не из фич. | AJTBD |
| P3 | Код — последнее средство. Перед разработкой обязателен гейт «можно ли проверить без кода». | NMT: challenge the build |
| P4 | Всё — файлы с фиксированными путями и ID. Каждое требование трассируется до Job. | BMAD: артефакты как контекст |
| P5 | Глубина процесса — по размеру задачи (треки S / M / L). | BMAD: scale-adaptive |
| P6 | Дизайн строится из контекста продукта и проверяется чек-листом антипаттернов, а не на глаз. Любой фронтенд сразу совместим с Impeccable. | Impeccable: идея контекста продукта и антипаттернов |

## 2. Что берём и что режем

### NMT / AJTBD
**Берём:** Core Job / Big Job, критерии успеха, цепочку шагов клиента, Aha Moment, идею каталога механик создания ценности, карточки допущений, гейт «challenge the build», идею формул Job-языка для текстов, правило «ввод = гипотеза», счётчик validation debt.
**Только идея (лицензия CC BY-NC-SA):** каталог механик и формулы текстов — свой состав, свои формулировки, свой порядок; списки источника не переносим даже пересказом.
**Режем:** трёхслойные отчёты и HTML-вывод, Deep-режим по умолчанию, оценку рынка (TAM/SAM), поиск альтернативных рынков, RICE на десятки гипотез. `analyze-interviews` и `diagnose` остаются опциональными, вне основного пайплайна.

### BMAD (база — стабильная v6.12)
**Берём:** цепочку артефактов PRD → архитектура → эпики/истории, короткие истории с AC «дано / когда / тогда», план истории, который пишется перед реализацией (а не заранее), гейт готовности к разработке (трассировка в обе стороны), минимальный контекст проекта (только неочевидное), цикл «план → реализация → независимое ревью» с тестами, состязательное ревью кода, вход по размеру задачи, шаг Learn & adjust.
**Режем:** персонажей-агентов (Analyst/PM/Architect/SM как отдельные роли), party mode, шардинг документов, sprint-планирование и статусы спринта, ретро как церемонию, enterprise-тестирование, game dev и creative-модули.

### Impeccable
**Берём идеи:** файл контекста продукта (генерируем из frame), файл дизайн-системы, цикл «сформировать → раскритиковать → проверить → отполировать», список антипаттернов ИИ-интерфейсов, проверку UX-текстов и устойчивости (пустые/ошибочные состояния), режим экрана (убедить / работать / читать).
**Совместимость (Impeccable-fitted):** любой фронтенд, собранный по FlashStart, сразу готов к работе с Impeccable: `PRODUCT.md` и `DESIGN.md` лежат в корне продукта в читаемом им формате (`PRODUCT.md` с разделом `## Platform`; `DESIGN.md` по открытой спецификации DESIGN.md — токены во frontmatter + стандартные разделы), UI проходит детектор `npx impeccable detect` без находок.
**Режем в MVP:** анимации, «вау»-эффекты, live-режим, тонкую стилизацию (смелее/тише).

### Политика оригинальности (решение автора)
Фреймворк оригинальный: из трёх источников берём **идеи и структуру**, все тексты, шаблоны и правила пишем заново своими словами. Ничего не копируем и не форкаем. Методология — собственная упрощённая версия, без ссылок на канон в теле скиллов. Источники вдохновения достаточно упомянуть в README.
- **Дизайн:** своя компактная библиотека правил и антипаттернов в `fs-design/references/` — смысловой чек-лист. Детектор Impeccable (`npx impeccable detect`, без установки скилла) — обязательная формальная проверка UI; если он недоступен, гейт пропускается с записью в `skipped_gates`. Скилл Impeccable — опциональная интеграция: если установлен, `fs-design` предлагает его команды.
- **Термины:** общие (Job, критерии успеха, Aha Moment, допущение) используем свободно. Фирменные названия чужих методик в названиях скиллов и артефактов не используем.

## 3. Пайплайн и треки

```
            ┌──────────── kill / pivot ◄──────────────┐
            ▼                                          │
fs-frame ─► fs-rat ─┬─(можно без кода)─► fs-test ─────► fs-learn
                    │                                  ▲
                    └─(нужен код)─► fs-spec ─► fs-plan ─► fs-build ⇄ fs-design ─► fs-ship
```

**Гейты предупреждают, а не блокируют.** Если гейт не пройден, скилл показывает, что именно не выполнено и какой риск это несёт. Пользователь может продолжить; пропуск записывается в `state.yaml` как `skipped_gates` и увеличивает validation debt.

| Трек | Когда | Шаги |
|---|---|---|
| **S — без кода** | главный риск проверяется без продукта: консьерж, ручная услуга, опрос, переписка, лендинг | frame → rat → test → learn |
| **M — малый билд** | нужен прототип, 1–3 эпика, стек очевиден | frame → rat → spec → build (+design) → learn; план встроен в spec |
| **L — полный билд** | новые интеграции, данные, нетривиальная архитектура | frame → rat → spec → plan → build (+design) → learn |

Трек выбирает `fs-rat` и записывает в состояние. Пользователь может переопределить.

## 4. Скиллы

| Скилл | Вход | Выход | Суть | Гейт выхода |
|---|---|---|---|---|
| `fs` | `.fs/state.yaml` | подсказка следующего шага | роутер и статус | — |
| `fs-frame` | идея (свободный текст) | `01-frame.md` | рынок и язык аудитории, сегмент, Core/Big Job, критерии успеха (SC), цепочка шагов, Aha Moment, механика ценности, таблица «что ты сказал → риск» | у каждого SC есть способ измерения |
| `fs-rat` | frame | `02-rat.md` | 3–5 конкретных допущений, ранжирование `(вероятность ошибки × ущерб) / стоимость проверки` (шкалы 1–5), «что выкинуть», самый дешёвый тест, kill-критерии, **выбор трека** | у топ-1 допущения есть тест и порог |
| `fs-test` | rat | `03-test.md` (+ тексты лендинга) | план no-code теста в подходящем формате (консьерж, ручная услуга, опрос, лендинг, демо-видео, переписка), тексты на Job-языке, метрики и сроки. Если нужен интерфейс — собирает `fs-design` | есть дата и порог решения |
| `fs-spec` | frame + rat | `04-spec.md`, `PRODUCT.md` (в корне продукта) | PRD-lite: FR со ссылками на SC, флоу по цепочке шагов, обязательный эпик Aha, топ edge cases, события аналитики из SC, kill/continue | проверка трассировки зелёная |
| `fs-plan` | spec | `05-architecture.md`, `project-context.md`, `stories/*.md` | стек и короткие ADR; эпики → короткие истории (цель, FR, AC «дано / когда / тогда», без задач); `project-context.md` — только неочевидное (команды, запреты, отклонения от умолчаний, наблюдённые ошибки), без пересказа кода; гейт готовности | у каждой истории есть FR и AC; у каждого FR есть история |
| `fs-build` | story-файл | код + тесты + `review.md` | цикл истории: план и задачи (дописываются в story-файл) → реализация и тесты → ревью двумя линзами («сломай это», граничные случаи) → триаж → DoD. История — одна цель, одна сессия | DoD (см. §6) |
| `fs-design` | `PRODUCT.md`, UI-истории | `DESIGN.md` (в корне продукта), UI | контекст из frame → бриф экрана с режимом (убедить / работать / читать) → формирование → критика → аудит по чек-листу и детектору → полировка; не больше 2 раундов визуальной проверки; если установлен Impeccable — предлагает его команды | чек-лист пройден, `impeccable detect` без находок |
| `fs-ship` | код / лендинг, `project-context.md` | `07-ship.md`, работающий URL | выбор хостинга по типу проекта, пошаговый деплой, домен и HTTPS, секреты, аналитика `EV`, предрелизный чек-лист (персональные данные, бэкапы) | URL открывается, события `EV` приходят |
| `fs-learn` | метрики / результаты теста | `06-learn.md` | факт против kill-критериев → continue / pivot / kill, обновление frame | решение записано |

Каждый SKILL.md — не больше ~300 строк: методика, шаблон артефакта, чек-лист. Длинное выносится в `references/`.

## 5. Контракт артефактов (ядро фреймворка)

### ID-схема
| Сущность | ID | Где рождается |
|---|---|---|
| Job | `J1`, `J2` | frame |
| Критерий успеха | `SC1.1` (SC 1 у J1) | frame |
| Допущение | `A1` | rat |
| Функц. требование | `FR1` | spec |
| Событие аналитики | `EV1` | spec |
| Эпик / история | `E1`, `S1.2` | plan (или spec в треке M) |

### Уровень уверенности у Job и SC
| Тег | Источник | Требование |
|---|---|---|
| `[head]` | голова фаундера | проходит «лезвие адекватности»: (1) можно назвать 3 конкретных людей с этой Job; (2) есть текущее решение, которым они пользуются сейчас; (3) понятно, что они теряют без продукта. Не прошёл — Job уходит в допущения `A`, а не в основу frame |
| `[interview]` | интервью, ≥3 совпадающих | основа для спеки без предупреждения |
| `[data]` | поведение / метрики | сильнее интервью |

Spec, построенный на `[head]`-Job, получает предупреждение и +1 к validation debt.

### Правила трассировки (проверяются скриптом `scripts/trace-check`)
1. Каждый `FR` ссылается хотя бы на один `SC`.
2. Каждый `SC`, на который ссылаются FR, имеет `EV` (иначе гипотезу нечем проверить после релиза).
3. Каждая история ссылается на `FR`, у каждой есть AC.
4. Эпик Aha Moment существует и стоит первым в треках M и L.
5. У каждого `A` со статусом `open` есть тест и kill-порог.
6. Validation debt = открытые `A` + пропущенные гейты (`skipped_gates`) + 1, если spec опирается на `[head]`-Job. Выводится в `fs` с разбивкой. *Формула предварительная — пересматривается по итогам прогона `examples/h-001`.*
7. Каждый `FR` покрыт хотя бы одной историей (трек L; в треке M — после spec).

Детали формата (frontmatter, `items`, маркеры AC, коды правил) — `docs/contract.md`.

### Frontmatter артефакта
```yaml
---
fs: spec            # тип артефакта
hypothesis: h-001
upstream: [01-frame.md, 02-rat.md]
ids: [FR1, FR2, EV1]
refs: {FR1: [SC1.1], FR2: [SC1.2], EV1: [SC1.1]}
status: draft       # draft | approved | superseded
---
```

### Состояние `.fs/state.yaml`
```yaml
hypothesis: h-001
track: M
stage: spec
validation_debt: 3
next: fs-build S1.1
```

## 6. Definition of Done для истории

- AC выполнены, тесты написаны и проходят.
- Состязательное ревью: найдено и закрыто не менее 3 проблем или явно записано «не найдено» с обоснованием.
- UI-история: чек-лист антипаттернов `fs-design` пройден, критика проведена, `npx impeccable detect` без находок (если детектор недоступен — пропуск в `skipped_gates`).
- События `EV`, связанные с историей, отправляются.
- `trace-check` зелёный.

## 8. План проверки работоспособности

1. **Сухой прогон на бумаге:** одна реальная гипотеза проходит frame → rat → spec вручную по шаблонам. Ищем, где информации не хватает для следующего шага.
2. **Трек S:** одна гипотеза доходит до запущенного no-code теста.
3. **Трек M:** один маленький прототип доходит до деплоя с событиями аналитики.
4. **Метрики фреймворка:** время до первого теста; доля гипотез, убитых до кода; число переделок после ревью; число нарушений чек-листа дизайна на релизе.
